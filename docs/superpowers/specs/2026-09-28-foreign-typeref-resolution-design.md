# Foreign TypeRef Resolution — Issue and Work

**Status:** incoming defect report, written from outside this repository.
**Found by:** the xflux project, generating its real catalog (`veh.common` +
`veh.cluster`) for the first time. **Verified against:** `92dcb73`
(`fork/feat/kotlin-runtime` tip), clean `--rerun-tasks` rebuild, pinned
`editor-v0.2.2` (`ridlc 0.2.1`).

## The symptom

A signal whose type is a **union declared in another package** kills the plugin:

```
java.lang.IndexOutOfBoundsException: Index: 1
  at ridl.codegen.kotlin.types.Wires.declarationOf(Wire.kt:135)
  at ridl.codegen.kotlin.types.Inits.ofRef(Inits.kt:25)
  at ridl.codegen.kotlin.types.Inits.ofRef(Inits.kt:26)
  at ridl.codegen.kotlin.types.FacesEmitter$Face.channelInit(FacesEmitter.kt:681)
error: plugin `ridlc-gen-kotlin` failed: exit status: 3
```

The path is `channelInit` → `Inits.ofRef` (the signal's type) →
`Inits.ofDeclaration` → the `UNION` branch at `Inits.kt:47`, which recurses with
`ofRef(arm.type)` → `Wires.declarationOf`, which indexes the wrong table.

The same union inside a **single** package generates correctly. The trigger is
foreignness, not unions.

## Reproduction

Self-contained, no xflux involvement.

`ridl/ridl.toml`

```toml
[workspace]
members = ["a", "b"]
```

`ridl/a/ridl.toml` → `[package]` `name = "a"`; `ridl/b/ridl.toml` likewise with
`name = "b"`.

`ridl/a/types.ridl`

```ridl
package a

type Small : integer [0..100] = 0

union Choice {
  small : Small
}
```

`ridl/b/api.ridl`

```ridl
package b

import a.Choice

interface Iface {
  signal pick: Choice @100ms
}
```

Then:

```
ridl build --out-dir out --plugin kotlin=<dist>/bin/ridlc-gen-kotlin ridl
```

Package `a` generates. Package `b` crashes.

## Root cause — upstream, in `ridl-ir`'s lowering

**This is not this repository's bug.** The plugin reads `model.proto` exactly as
written; the model it is given violates that schema.

`crates/ridl-ir/proto/ridl/codegen/v1/model.proto`:

```proto
message TypeRef {
  string reference = 1;
  bool resolved = 2;
  // The declaring package, when resolved.
  string package = 3;
  // `package` is not `Scope.package`.
  bool foreign = 4;
  // Into `Model.declarations` when local, into `Model.foreign` when foreign.
  uint32 index = 5;
  DeclKind kind = 6;
}
```

The captured `CodegenRequest` for package `b`:

```
Model.scope        = {"package": "b", "others": ["a", "b"]}
Model.declarations = []                        // b declares no types at all
Model.foreign      = [ (a, Choice), (a, Small) ]

// the arm of the foreign union a.Choice, as inlined into b's model:
{"reference":"Small","resolved":true,"package":"a","foreign":false,"index":1}
```

`ref.package` is `"a"`; `Scope.package` is `"b"`. By the schema's own wording,
`foreign` **must** be `true`. It is `false`, so `declarationOf` takes the local
branch and calls `model.getDeclarations(1)` on an empty list.

The important detail, because it narrows the upstream fix to one field: `index`
is **already correct for the foreign table** — `Model.foreign[1]` is `a.Small`.
In package `a`'s own model the same arm is `{foreign:false,
index:0}`, correctly
addressing `a.declarations[0]`. So the lowering already re-indexed the arm into
`b`'s foreign table when it inlined the declaration, and simply failed to set
the flag to match. Likely one assignment in
`crates/ridl-ir/src/codegen/lower.rs`, on the path that inlines a foreign
declaration's members.

**Also worth reporting upstream:** `ridl build --emit rust` emitted
`veh.cluster.rs` _successfully_ for the equivalent input. If the Rust backend
also trusts `foreign`, it may be resolving against the wrong table and silently
emitting wrong code rather than crashing. That would make the upstream defect
considerably more urgent than a Kotlin-only crash. Worth checking before filing,
so the issue carries the right severity.

## What to do here

### 1. Close the corpus gap — the highest-value change

This survived a PR full of new tests because **no corpus entry imports from
another package**:

| entry        | package                | imports | union          |
| ------------ | ---------------------- | ------- | -------------- |
| `cabin`      | `veh.cabin`            | —       | —              |
| `fb-demo`    | `fb.demo`              | —       | `Outcome`      |
| `kt-values`  | `kt.values`            | —       | —              |
| `veh-common` | `veh.common` (`.typl`) | —       | `SensorResult` |
| `veh-cruise` | `veh.cruise`           | —       | `Command`      |

Unions are covered, but only locally, so `TypeRef.foreign` recursion is never
generated by any test. `veh-common` already exists as a standalone package
declaring a union; giving `veh-cruise` an `import veh.common.SensorResult` and a
signal typed on it reproduces this in the suite. Add that first, watch it fail,
and it guards the whole class of defect rather than this one instance.

Cross-package coverage is worth having for its own sake: `Wires.declarationOf`
has two branches and only one is exercised.

### 2. Never exit 3 on a model fact

`Main.kt` states the contract:

> "Every failure the host can read is a response and exit 0; anything thrown is
> written to standard error with its stack and is exit 3, which the host reports
> as a failed plugin."

and `Refusal.kt`:

> "It is thrown where it is found, caught per declaration, and reported as one
> error diagnostic, so every declaration the plugin refuses is named in one
> response."

An out-of-range index escaping as `IndexOutOfBoundsException` is therefore a
defect against this repository's own design, independently of the upstream bug:
a malformed model should be a diagnostic naming the declaration, not a stack
trace. `Wires.declarationOf` (`Wire.kt:129-137`) indexes both repeated fields
directly; bounds-check each and `refuse(...)` with the reference, the table
consulted and its size — e.g. _"the reference `Small` resolves to index 1 of
package b's 0 local declarations"_. That message alone would have identified
this in seconds.

This is worth doing whatever happens upstream.

### 3. Decide whether to work around the bad flag

`ref.package` is present and correct in both the local and foreign cases, so
foreignness can be derived as `ref.package != model.scope.package` instead of
trusting `ref.foreign`, and that agrees with the flag wherever the flag is
right. That would unblock cross-package generation without waiting for a ridl
release.

The cost is that the plugin then compensates for a schema violation rather than
the schema being fixed, and the workaround is easy to forget once upstream
lands.

Suggested split: land 1 and 2 now; take 3 only if cross-package generation is
needed before the next ridl release, and if so mark it clearly as a workaround
citing the upstream issue, so it can be removed rather than becoming folklore.

Note that `FacesEmitter.kt:719` already guards
`if (named.ref.foreign)
refuseClause("the subject is declared in another package")`
before calling `declarationOf`, so the codebase is already aware foreign refs
need care in this area; `Inits` simply has no equivalent.

## Why this matters downstream

xflux's shipping catalog is `veh.common` + `veh.cluster`, with
`signal powertrainInfo: PowertrainInfo` where `PowertrainInfo` is a union
declared in `veh.common`. That is the first real-world input to hit this, and it
blocks generating the Kotlin side of that catalog.

It is not blocking xflux overall: a single-package `.ridl` generates correctly
today, so the mock-bus work can proceed on one, and the cross-package catalog
waits on this. No urgency is implied beyond the Rust-backend question in "Root
cause", which may be more serious than the crash.
